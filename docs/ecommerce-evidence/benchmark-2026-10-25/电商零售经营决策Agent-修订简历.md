# 电商零售经营决策 Agent

2026.07–至今

面向商品、SKU、订单、库存与竞品经营异常，构建覆盖数据接入、异常调查、决策建议、人工审批和安全执行的 Agent 决策闭环，并在本地测试环境完成采购与到货验证。

- **经营数据接入与 Tool Calling：** 定义商品、订单和竞品三类数据契约，统一 SKU、库存、安全库存、订单状态、来源和采集时间；通过结构化工具调用完成商品、订单、竞品查询与本地经营规范检索，在 60 条合成经营任务的确定性对照回放中，完整调查所需工具调用步骤由 360 次降至 240 次，减少 33.3%。
- **Context Engineering 与任务规划：** 使用 PromptPlan 分层装配经营与安全规则，查询证据和未知信息按任务作为工具结果进入上下文；将完整任务状态保存在业务库，对话中传递任务编号和阶段摘要，相比每步回传完整状态，同批 60 条任务的交互载荷估算 Token 总量由 62.6 万降至 8.56 万，减少 86.3%。
- **阶段化经营决策 Workflow：** 将经营异常拆为 Monitor、Detect、Investigate、Decide 四个阶段，串联商品、订单和竞品查询；通过阶段状态守卫与 Evidence Chain 记录工具参数、采集时间、调查依据和阶段结论，支持补充业务口径后重新调查并生成建议。
- **安全执行与副作用隔离：** 将经营建议、人工审批和测试执行分开，采购方案绑定具体 SKU、数量和供应商；只读预览不改数据，审批后才在测试库创建采购单并增加在途量，到货登记后才增加库存，结合事务、幂等键和持久化回执防止重复执行。
- **Agent Eval 与回归验证：** 针对阶段跳转、SKU 证据错配、库存口径缺失、数据过期、审批冲突、重复执行和事务回滚七类风险建立回归场景，校验工具参数、调查证据与执行边界；60 条对照任务的原始取证、事实分析与建议一致，当前相关回归 22 项通过，含 7 项 MySQL 集成。

## 上述指标的面试口径

第一条：本次基准设定了两条确定策略。基线需要 start、商品、订单、竞品、investigate、decide 共6次；当前链路是 start 和3次 advance 共4次。60个任务分别为360和240。没有调用真实模型自动选工具，所以说“确定性对照回放的调用步骤”，不能说“线上Agent调用减少33.3%”。

第二条：把同一任务四阶段的请求和响应序列化后计量，比较“回传完整状态”和“只传任务标识并返回摘要”。62.6万与8.56万是60任务载荷估算Token之和，不是单次请求窗口，不是模型账单，也不是Pi压缩算法的效果。无关系统提示词和工具描述在本实验之外。

第三条：固定规则负责数字计算和关键字段判断，LLM理解问题、选工具、解释结果。不能说所有facts/inferences都由大模型自由推理。

第四条：测试库发生真实数据库写入，尚未接生产ERP或真实商家接口。人工补口径和登记到货不属于Agent可自主调用的权限。

第五条：这是确定性工程回归，真实模型工具选择成功率、自然语言任务成功率和经营收益尚未测量。
