# 当前项目怎么理解

更新日期：2026-10-23。说明对应当前源码；测试环境闭环不等于已经接入真实商家或生产平台。

## 这次具体改了什么

- 删除旧 JSON 读数据 Adapter、旧工具和 IPC 入口、旧审批与 simulation/external 执行器；正常运行只走 MySQL 电商链路。
- 删除旧 JSON 样本文件，初始化演示商品改用 `src/ecommerce/test-fixture.ts`，仅在导入时插入 MySQL。之后查询和修改的是 MySQL，不是修改 fixture 文件。
- 删除旧链路测试及旧人工 benchmark 脚本，增加当前 Workflow 顺序、证据一致性等回归。旧 benchmark 不再作为指标来源。
- 删除 Workspace Memory 召回诊断返回值、诊断日志和召回界面事件；SOP 不返回召回统计。仍保留记忆本身的来源与版本、文档引用、业务证据链、审批和库存流水。
- 电商工具规则不再靠用户输入关键词或正则触发。工具可用就加入短规则，跟进时不丢失约束；不额外调用模型分类。
- 保留 MySQL 的人工审批、只读预览、真实测试采购、到货入库、持久化幂等和事务。

旧 SQLite 审批表的历史迁移不改写，也不删除数据库里已有历史行。旧源码入口和编译产物移除后，该表不再驱动任何旧链路。

## 一个 SKU 的完整例子

1. 用户问“SKU-002 需要补货吗？”模型根据工具说明调用 `ecommerce_test`。
2. `start` 按这个 SKU 查 MySQL，创建调查任务：库存 80、安全线 150，低于安全线 70。没有指定 SKU 时，`monitor` 按页查低库存记录，不把整库塞给模型。
3. `advance` 按预定义顺序执行 Detect、Investigate、Decide。每次携带任务 ID 和期望版本，服务端读取并更新 MySQL 状态；事实、推断和未知项保存在任务里。
4. 调查结果是“考虑补货”和待确认条件。`consider_restock` 就是“考虑补货”的建议类别，不是采购命令。差值 70 不代表最优采购量。
5. 人工补充测试口径，刷新任务重新查证，提出明确数量和供应商的方案并审批。
6. `apply(test)` 真实建采购单并增加在途量，库存仍为 80；货还没到，不能说库存已经增加。
7. 人工登记测试到货后，库存增加到 150，同时减少在途量并写流水。重试用同一幂等键，返回原回执。

当前主要模型工具只有两个：`ecommerce_test` 处理结构化业务，`ecommerce_sop_search` 检索规范。页面上的人工审批和到货操作是 HTTP 接口，不是模型可自行调用的权限。

## 为什么现在仍然有 SQLite 和 MySQL

这是应用职责的划分，不是 Agent 必须搭配两个数据库，也不是“文本必须放 SQLite、结构化数据必须放 MySQL”。两种库都能保存文本和结构化记录。

| 内容           | 当前保存位置                                   | 举例                                                               |
| -------------- | ---------------------------------------------- | ------------------------------------------------------------------ |
| 电商业务       | MySQL 的 `ec_*` 表                             | 商品、订单、Workflow、审批、采购单、执行回执、库存流水             |
| 宿主平台数据   | `data/db/messages.db`（SQLite）                | 消息、工作区、平台配置及 Workspace Memory 等现有平台状态           |
| 长期记忆       | 上述 SQLite 中的 `workspace_memory_items` 等表 | “这个工作区采用先审批后采购”、历史决策、经验；带来源、版本、有效期 |
| Pi 会话历史    | Runner 的会话目录中的 JSONL 文件               | 本会话的用户消息、助手回答和工具结果；恢复与压缩由 Pi 管理         |
| 操作规范知识库 | `docs/ecommerce-sop/*.md`                      | 采购和到货的区别、审批规则、幂等重试规则                           |

保留 SQLite 的原因是宿主已经把消息、工作区、记忆等能力做在里面；本次电商清理没有重写整个宿主。它是应用读取的本地数据库文件，不需要用户再启动一个 SQLite 服务器。MySQL 测试实例独立启动，用来实际验证电商事务和数据变更。

如果以后明确要求“所有宿主持久化统一到 MySQL”，需要同时迁移表结构、查询、全文检索、事务、历史数据、备份和部署流程。不能只换连接地址。本次没有完成这类全平台迁移，也没有新增 Redis 或 Milvus。

SQLite 的基本使用同样是表、行、SQL 查询和事务。当前先理解“记什么、何时查、何时更新、怎么隔离”，可以暂时不学习它的分词器细节。

## 系统提示词如何进入模型

`pi-index.ts` 调用 PromptPlan，把平台身份、交互、安全、记忆使用规则、输出要求、电商工具规则和渠道要求组装为系统提示词。

本次选择“按工具能力固定附加短规则”：当前 Runner 注册了两个电商工具，所以始终附加电商规则；没有电商工具的调用方可以传 `false` 不附加。规则以“使用电商工具时适用”开头，不要求普通聊天查库存。

这样用户说“继续”“查一下那个商品”也不会漏注入规则，不需要先写一套中文关键词表，也不增加一次模型调用。模型负责理解问题并选择工具；程序负责把已确定的工具规则放入提示词。后端权限、审批和事务独立执行，即使模型忽略提示词也不能因此获得审批权。

## 现在有 RAG 吗

有一个小型的本地文档词法 RAG：

```text
问题 → ecommerce_sop_search → 读取本地 SOP、按标题分段
     → BM25 对相关段落排序 → 返回段落与来源
     → 工具结果进入模型上下文 → 模型结合资料回答并引用
```

SOP 是 Standard Operating Procedure，意思是“标准操作流程/规范”。比如用户问“为什么已经采购，库存还没增加”，检索返回“采购只增加在途，到货登记才增加实物库存”的规范段落。

本地文档完全可以作为 RAG 的知识源；RAG 不要求先有向量库。当前按词语匹配和相关性排序，没有 embedding、语义相似度、Milvus 或 LLM Wiki。不把“低库存”与“缺货风险”等复杂同义表达的召回效果当成已经验证。

`SKU-002 现在有多少库存` 应查 MySQL，不能查规范找历史数字。SOP 是规则知识，Workspace Memory 是已保存的历史事实/经验，当前库存是业务事实，三者不能混用。

段落返回文件路径、起始行、版本哈希，方便核对回答引用。这些来源信息继续保留；已删除的是“本轮召回了哪些记忆、跳过哪些、注入哪版”等额外诊断事件和统计，不是删除业务证据。

## 长期记忆预算和会话压缩

Pi 的会话历史及其 compaction 负责短期会话连续性。长期记忆另由应用选择后附到本轮消息中，二者共享最终模型上下文，不是两个互不影响、无限容量的区域。

长期记忆有整批总字符预算：已经放入的内容也计入预算；某条放不下，本轮跳过它，继续试后面的较短条目。原文还在数据库，没有被删除。多个小条目加起来超过预算时，只选择能放下的部分，不会把已经选好的全部扔掉；需要细节可用 `workspace_memory_get` 按需读取。

写入规则现在明确要求一个条目只存一个简短持久事实，长材料先提炼、按主题拆条、保留来源引用。该步骤由调用记忆工具的模型按提示完成；没有新增一个后台自动摘要服务，也不会自动压缩库里所有旧长记录。不能把这个规则描述成已经实现了服务端语义压缩算法。

## 可以据实讲给面试官

> 我把电商调查和执行状态存入 MySQL，模型只携带任务 ID 和版本，避免每次回传完整状态。模型负责理解任务、调用工具和解释证据，业务服务负责库存计算、审批校验和事务。操作规范采用本地 BM25 检索，返回段落来源后用于回答。短期会话复用 Pi 的历史和压缩机制；宿主已有的长期记忆保留在 SQLite，按工作区隔离和预算选取。电商工具启用时固定加载简短规则，不使用额外模型做主题分类。当前验证的是本地测试采购和到货闭环，没有宣称生产上线。
